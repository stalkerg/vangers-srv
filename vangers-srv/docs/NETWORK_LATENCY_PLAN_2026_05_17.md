# План исправления сетевой задержки и накопления realtime-пакетов

Дата: 2026-05-17

Документ фиксирует текущий план работ по Rust-серверу Vangers и C++-клиенту.
Цель — снизить application latency в мультиплеере без изменения протокола и без
потери критичного состояния игры.

## Текущий статус

На 2026-05-17 выполнены первые безопасные слои плана:

1. C++-клиент больше не создаёт очередь из множества outstanding
   `SERVER_TIME_QUERY`: следующий запрос отправляется только когда нет pending
   ответа.
2. C++-клиент больше не использует сырой `average_lag` как неограниченный
   интервал отправки мехоса: интервал отправки `UPDATE_OBJECT` ограничен
   диапазоном 50..150 ms.
3. Rust-сервер отправляет `SERVER_TIME` через per-client latest-only slot:
   старый pending `SERVER_TIME` заменяется новым и не стоит в общей FIFO.
4. Rust-сервер отправляет realtime `UPDATE_OBJECT` мехосов (`NID_VANGER`) через
   per-client latest-only map по ключу `object_id`: pending update того же
   объекта заменяется новым.

Сознательно НЕ сделано:

- latest-only пока не включён для `DEVICE`, `SLOT`, `STUFF`, `GLOBAL`, `TNT`,
  `SENSOR`, `TERRAIN`;
- `CREATE_OBJECT`, `DELETE_OBJECT`, `HIDE_OBJECT`, `DIRECT_RECEIVING`,
  `PLAYERS_*`, `SET_WORLD_RESPONSE` остаются reliable;
- visibility/resync logic старого C++-сервера пока не переносилась.

## Главная гипотеза

По клиентским и серверным логам проблема больше похожа не на CPU/logging
bottleneck, а на накопление устаревших realtime-пакетов:

1. `SERVER_TIME` ответы могут копиться и приходить пачками.
2. Клиент использует `average_lag` как интервал отправки своего мехоса.
3. При скачке `average_lag` до 500–1000 ms клиент начинает реже отправлять
   `UPDATE_OBJECT`.
4. Для realtime-состояния это создаёт positive feedback loop:
   старые ответы портят lag estimate, высокий lag estimate уменьшает частоту
   отправки, остальные игроки видят более старое состояние.

Основной принцип исправления:

- reliable-состояние нельзя терять;
- realtime-состояние нельзя долго копить;
- старый `UPDATE_OBJECT` почти всегда хуже, чем более новый `UPDATE_OBJECT`;
- старый `SERVER_TIME` вреден для оценки задержки.

## Почему measured lag сейчас связан с отправкой мехоса

На момент составления плана `average_lag` в C++-клиенте связан с частотой
отправки мехоса напрямую.

Сетевой lag записывается в `average_lag` при обработке `SERVER_TIME`:

```cpp
average_lag = dt;
```

Файл:

```text
src/network.cpp
```

Также `average_lag` выставляется во время синхронизации времени:

```cpp
average_lag = round(response_time*1000);
```

Файл:

```text
src/network.cpp
```

Затем это же значение используется как минимальный интервал между отправками
сетевого состояния мехоса:

```cpp
if(need_to_send_vanger && IS_PAST(last_send_time + average_lag)){
    last_send_time = SDL_GetTicks();
    NETWORK_OUT_STREAM.update_object(NetID,R_curr.x,R_curr.y);
    ...
    Send();
}
```

Файл:

```text
src/units/mechos.cpp
```

То есть текущая логика фактически такая:

```text
average_lag = 100 ms
=> мехос отправляется не чаще чем раз в 100 ms

average_lag = 500 ms
=> мехос отправляется не чаще чем раз в 500 ms

average_lag = 1000 ms
=> мехос отправляется не чаще чем раз в секунду
```

Это не меняет локальную физику мехоса, но напрямую ухудшает частоту отправки
его `UPDATE_OBJECT` другим игрокам.

Дополнительно `SERVER_TIME_QUERY` сейчас отправляется рядом с отправкой мехоса:

```cpp
if(lag_averaging_t0.tell() < 20){
    NETWORK_OUT_STREAM.begin_event(SERVER_TIME_QUERY);
    ...
    lag_averaging_t0.put(SDL_GetTicks());
}
```

Поэтому получается опасная петля:

```text
частота отправки мехоса зависит от average_lag
average_lag обновляется через SERVER_TIME
SERVER_TIME_QUERY отправляется рядом с отправкой мехоса
```

Если старые `SERVER_TIME` ответы накопились и пришли пачкой, `average_lag` может
стать завышенным. После этого клиент начинает реже слать мехос, а значит другие
игроки получают более редкие и более старые `UPDATE_OBJECT`.

Именно поэтому в плане отдельно выделены две задачи:

1. исправить измерение lag, чтобы клиент не держал много outstanding
   `SERVER_TIME_QUERY`;
2. отделить measured lag от интервала отправки мехоса, чтобы плохой или
   испорченный lag estimate не мог полностью задушить realtime updates.

## Этап 1. Починить измерение lag на клиенте

Статус: выполнено.

### Что изменить

В C++-клиенте ограничить количество одновременно ожидающих
`SERVER_TIME_QUERY`.

Сейчас клиент может держать несколько запросов одновременно. Если ответы
приходят пачкой, `average_lag` начинает отражать не реальный RTT, а время,
которое ответы пролежали в очередях.

Нужно сделать так, чтобы клиент не слал новый `SERVER_TIME_QUERY`, пока не
получен ответ на предыдущий запрос. Минимальная правка:

```cpp
if (lag_averaging_t0.tell() < 1) {
    ...
}
```

вместо более высокого лимита outstanding-запросов.

### Почему это безопасно

Это не меняет игровой протокол и не меняет семантику `SERVER_TIME`.
Клиент просто перестаёт сам создавать очередь старых ping-запросов.

### Ожидаемый результат

- В клиентском логе исчезают пачки `SERVER_TIME` в один кадр.
- `average_lag` становится ближе к реальному RTT.
- Снижается шанс, что клиент сам начнёт слать мехос слишком редко.

## Этап 2. Разделить measured lag и интервал отправки мехоса

Статус: выполнено.

### Что изменить

Не использовать сырой `average_lag` напрямую как интервал отправки
`UPDATE_OBJECT` для мехоса игрока.

Ввести отдельный bounded interval, например:

```cpp
int vanger_send_interval = clamp(average_lag, 50, 150);
```

И использовать его для проверки отправки мехоса:

```cpp
IS_PAST(last_send_time + vanger_send_interval)
```

Точные значения надо подтвердить тестами. Начальный осторожный вариант:

- минимум: 50 ms;
- максимум: 150 ms.

### Почему

`average_lag = 700 ms` не должен означать, что клиент отправляет позицию мехоса
раз в 700 ms. Даже при плохом ping сервер должен получать достаточно частые
обновления realtime-состояния.

### Почему не фиксировать сразу 50 ms

Фиксированный интервал может увеличить сетевой трафик и сильнее изменить
поведение игры. Bounded interval осторожнее:

- сохраняет связь с реальным состоянием сети;
- не даёт плохому ping полностью задушить updates;
- проще сравнивать с текущими логами.

## Этап 3. Разделить серверные пакеты на reliable и realtime/latest-only

### Reliable packets

Эти пакеты нельзя терять и нельзя заменять более новыми без понимания
семантики:

- `ATTACH_TO_GAME_RESPONSE`
- `RESTORE_CONNECTION_RESPONSE`
- `SET_WORLD_RESPONSE`
- `GAME_DATA_RESPONSE`
- `TOTAL_LIST_OF_PLAYERS_DATA`
- `PLAYERS_NAME`
- `PLAYERS_POSITION`
- `PLAYERS_WORLD`
- `PLAYERS_STATUS`
- `PLAYERS_DATA`
- `PLAYERS_RATING`
- `CREATE_OBJECT`
- `DELETE_OBJECT`
- `HIDE_OBJECT`
- `DIRECT_RECEIVING`

Они должны идти через reliable FIFO и не должны silently drop-аться.

### Realtime / latest-only packets

Эти пакеты не должны долго стоять в FIFO:

- `UPDATE_OBJECT`
- `SERVER_TIME`

Для них старое состояние почти всегда вреднее, чем отсутствие старого состояния.
Их надо либо дропать при перегрузе, либо заменять более новым состоянием.

## Этап 4. Сделать latest-only обработку для SERVER_TIME

Статус: выполнено на Rust-сервере.

### Что изменить на Rust-сервере

`SERVER_TIME` не должен накапливаться в per-client FIFO.

Возможные реализации:

1. Если для клиента уже есть pending `SERVER_TIME`, заменить его новым.
2. Если для клиента уже есть pending `SERVER_TIME`, не добавлять ещё один.
3. Хранить только одно последнее значение `SERVER_TIME` в realtime-очереди.

### Почему

Старый `SERVER_TIME` портит RTT estimate. Если клиент получает пачку старых
ответов, он может завысить `average_lag`.

### Проверка

В клиентских логах не должно быть длинных пачек `IN SERVER_TIME` в одном кадре.

## Этап 5. Сделать latest-only обработку для UPDATE_OBJECT

Статус: выполнено только для `NID_VANGER`.

### Что изменить на Rust-сервере

Для `UPDATE_OBJECT` использовать ключ:

```text
(recipient_client_id, object_id)
```

Если сервер ещё не отправил старый update для этого объекта этому клиенту, новый
update должен заменить старый:

```text
object 123 -> x=100
object 123 -> x=120
object 123 -> x=140
```

Отправлять клиенту надо только последнее состояние:

```text
object 123 -> x=140
```

### Почему

Старые координаты не нужны для realtime-релея. Они создают head-of-line blocking
и увеличивают видимую задержку.

### Важное ограничение

Эта логика должна применяться только к явно заменяемым realtime
`UPDATE_OBJECT`.
Нельзя аналогично заменять:

- `CREATE_OBJECT`;
- `DELETE_OBJECT`;
- `HIDE_OBJECT`;
- `DIRECT_RECEIVING`;
- `PLAYERS_*`;
- `SET_WORLD_RESPONSE`.

Эти пакеты несут состояние, порядок и факт доставки которых важны.

### Текущая безопасная реализация

В первом серверном патче latest-only включён только для `NID_VANGER`, то есть
для realtime-положения мехосов. Это самый безопасный слой:

- старые координаты мехоса бесполезны, если уже есть более свежие;
- именно мехосы создают заметную "ватную" сетевую задержку;
- предметы, трюм и ownership-события пока не затронуты.

Обычный `Client::send(UPDATE_OBJECT)` теперь остаётся reliable. Для
coalescing используется отдельный путь `send_realtime_update()`, который
вызывается только из обработчика live `UPDATE_OBJECT` мехоса.

Дополнительно `DELETE_OBJECT` и `HIDE_OBJECT` удаляют pending realtime update
того же `object_id`, чтобы клиент не получил старый `UPDATE_OBJECT` после
жизненно-циклового события удаления/скрытия.

### Что может остаться на будущее

Если после совместных тестов backlog всё ещё будет заметен, надо по логам
проверить, какие типы объектов создают очередь. Только после этого можно
рассматривать расширение latest-only на другие типы. До такого доказательства
не трогать `DEVICE`, `SLOT`, `STUFF` и глобальные события, потому что они
связаны с инвентарём/трюмом/ownership.

## Этап 6. Переработать writer loop сервера

Статус: частично выполнено.

Writer для клиента должен:

1. Отправлять reliable-пакеты без потери.
2. Периодически flush-ить latest realtime-состояние.
3. Не позволять realtime-спаму навсегда задерживать reliable-пакеты.
4. Не позволять reliable-бэклогу навсегда удерживать старые realtime-пакеты.

Ориентировочная частота realtime flush:

- 20 Hz как самый conservative вариант;
- 30 Hz как более плавный вариант;
- 60 Hz только если тесты покажут, что это не создаёт лишнего трафика.

На первом этапе лучше не менять протокол и не объединять несколько событий в
новый binary packet. Достаточно изменить стратегию очередей и отправки.

Сейчас writer:

1. сначала проверяет latest-only `SERVER_TIME`;
2. затем отправляет один reliable FIFO packet, если он уже есть;
3. затем отправляет один latest-only realtime `UPDATE_OBJECT`;
4. если ничего нет — ждёт события из FIFO, SERVER_TIME slot или realtime update
   map.

Это сохраняет приоритет reliable-событий и одновременно не даёт копиться
старым realtime-состояниям.

## Этап 7. Проверить world switch backlog

В логах встречалось:

```text
client outgoing queue full; reliable fallback send spawned
```

особенно во время `LEAVE_WORLD` / `HIDE_OBJECT`.

После разделения reliable/realtime очередей надо проверить:

- остались ли reliable fallback events;
- сколько `HIDE_OBJECT` создаётся при `LEAVE_WORLD`;
- не отправляются ли клиенту заведомо устаревшие world events;
- не мешает ли world-switch поток reliable-пакетов realtime-обновлениям после
  выхода в новый мир.

Важно: не удалять `HIDE_OBJECT` и не менять world-switch semantics без отдельного
доказательства. Эти события могут быть нужны для корректной синхронизации.

## Этап 8. Только потом смотреть visibility/resync

Если после исправления очередей игроки всё ещё иногда не видят друг друга,
тогда отдельно исследовать:

- `SET_POSITION`;
- периодический `PLAYERS_POSITION`;
- snapshot игроков после `SET_WORLD`;
- visibility logic старого C++-сервера;
- необходимость resync-пакетов для игроков, которые долго не видели друг друга.

Это второй слой. Его не стоит смешивать с исправлением latency/backlog, иначе
будет сложно понять, какая правка реально помогла.

## Минимальный первый patch

Рекомендуемый порядок первой реализации:

1. Клиент:
   - максимум один outstanding `SERVER_TIME_QUERY`;
   - отдельный bounded interval для отправки мехоса.
2. Сервер:
   - reliable-пакеты оставить без потери;
   - `SERVER_TIME` сделать latest-only или no-queue-old;
   - затем `UPDATE_OBJECT` сделать latest-only по `(recipient, object_id)`.

## Критерии успеха

После правок в логах ожидается:

- нет длинных пачек `SERVER_TIME` в одном кадре;
- `average_lag` не улетает в секунды из-за старых ответов;
- `UPDATE_OBJECT` не стоит в длинной FIFO-очереди;
- `client outgoing queue full` либо исчезает, либо остаётся только на тяжёлых
  world-switch сценариях;
- при плохом ping клиент всё равно шлёт мехос с bounded cadence, а не раз в
  500–1000 ms;
- reliable-события не теряются.

## Что не делать в рамках этого плана

- Не менять binary protocol.
- Не объединять события в новый packet type.
- Не дропать reliable-события.
- Не чинить visibility/resync одновременно с queue/backlog.
- Не делать выводы по одиночным solo-логам о баге синхронизации нескольких
  игроков без совместной тестовой сессии.
